Key Findings

Finding 1

Both architectures floor at ~0% Final Pass Rate

Neither Single-React (0.2% mean) nor Planner-Executor (0.0% mean) produces plans that pass all constraints. The headline metric of the TravelPlanner benchmark shows no discrimination between architectures at this model scale.

Finding 2 — Root Cause

Qwen2.5-7B fabricates sandbox entities

The model writes invented flight numbers (F1234567), hotel names (The Venetian Resort), and restaurants (Pancake House) that do not exist in the TravelPlanner database. The is_valid_information_in_sandbox check rejects any such plan immediately, preventing any commonsense or hard constraint evaluation.

Finding 3

Architecture reversal: SR outperforms PE on every metric

Single-React scores higher than Planner-Executor on delivery (+30.5pp), commonsense micro (+20.5pp), and final pass rate (+0.2pp). This is the opposite of the GPT-4o pilot result and indicates the planner stage is net-negative at 7B scale.

Finding 4

Planner stage eats the step budget

Planner-Executor uses ~1.48× more tokens (120k vs 81k/query) and takes ~1.48× longer (77s vs 52s). More critically, the planner's structured JSON call occupies context space, leaving the executor with fewer effective steps before hitting the 30-step cap — explaining the 30.5pp delivery gap.

Finding 5

Partial credit (CS micro) shows real signal

Commonsense micro-pass rate (fraction of individual checks satisfied) is 47.8% for Single-React and 27.3% for Planner-Executor. Plans score between 3–7 out of 8 checks, meaning plans are structurally valid — the sole blocker is entity fabrication, not planning logic.

Finding 6

Model capability is the binding constraint

TravelPlanner's own fine-tuned Qwen2-7B (SFT) also scores 0.0% final pass rate. This confirms the 7B parameter class is below the capability threshold required for this benchmark regardless of architecture. The architectural effect observed with GPT-4o requires sufficient base model grounding ability.

Root Cause: Entity Fabrication

Primary failure mode: is_valid_information_in_sandbox rejects plans that reference any entity (flight number, hotel, restaurant, attraction) not returned by a tool call. Qwen2.5-7B consistently ignores tool observations and writes plausible-but-invented names.

Example fabricated plan from seed 0, query 14 (easy, 3-day trip St. Louis → Las Vegas):

Day 1 — Transportation: Flight Number: F1234567, from St. Louis to Las Vegas
Accommodation: The Venetian Resort, Las Vegas
Dinner: Hu Niu Steakhouse, Las Vegas
↑ None of these entities exist in the TravelPlanner sandbox database

The FlightSearch tool was called and returned real flight numbers — but the model ignored the observation when writing the final plan.

Interpretation for RQ1

Architecture effect requires sufficient base model capability. The architectural advantage of Planner-Executor — demonstrated clearly at GPT-4o scale (11.7% vs 0%) — does not manifest at 7B scale because entity grounding is the binding constraint for both architectures. Until a model reliably quotes tool observations into its final plan, the structural guidance provided by the planner stage cannot be measured.
The 30-step Qwen2.5-7B results are a valid secondary finding: they establish the model capability boundary below which architectural differences are undetectable on TravelPlanner. This boundary sits somewhere between 7B and GPT-4o class, and the 50-step run currently in progress will confirm whether increasing the step budget shifts the delivery rate enough to change the picture.
Primary RQ1 evidence remains the GPT-4o pilot (3 seeds, n=20 each, Final Pass Rate 11.7% vs 0%, Commonsense macro 40–65% vs 0%). The Qwen validation results are reported as a model-scale ablation showing the effect is contingent on base model strength.
